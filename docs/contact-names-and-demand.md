# Nomes, leitura e mídia sob demanda

A migration `20260910000000_contact_names` acrescenta `Contact.nameMetadata` ao PostgreSQL. Execute `npm run db:migrate` antes de iniciar a API atualizada. O campo `Contact.name` continua sendo o rótulo de exibição interno; a metadata preserva separadamente nome da agenda, nome de perfil e dados legados.

Nos webhooks `contacts.set`, `contacts.upsert` e `contacts.update`, `name` e `savedName` representam somente o nome da agenda informado pelo provedor. `notify` e `verifiedName` são alternativas quando não há nome salvo. `nameSource` identifica `saved`, `notify`, `verified` ou `legacy`. Linhas antigas cuja origem é desconhecida são reexportadas como `legacyName`, sem promover esse valor a nome salvo.

`savedNameUpdatedAt` é o horário ISO da última observação aceita do nome da agenda, capturado antes da fila de importação e persistido. Não é um timestamp fornecido pelo WhatsApp. Replays do armazenamento preservam esse horário. Uma observação mais recente avança esse limite mesmo quando o texto é igual, impedindo que uma alteração intermediária atrasada restaure um nome antigo. Um `name` omitido ou `undefined` não remove o nome salvo; uma alteração explícita `name: null` ou `name: ""` produz `savedName: null` com seu horário. O consumidor deve comparar esse horário antes de aplicar alterações ou remoções. A API também impede que um replay antigo restaure um nome removido. Atualizações repetidas sem mudança de valor/proveniência não executam `UPDATE`; repetições idênticas adjacentes no mesmo lote compartilham uma consulta sem alterar as contagens dos webhooks.

O Baileys instalado define `Contact.name` como nome salvo e `Contact.notify` como nome de perfil: [tipos oficiais](https://github.com/WhiskeySockets/Baileys/blob/master/src/Types/Contact.ts). A API preserva essa distinção nos eventos e na reimportação. Dados ausentes no provedor permanecem desconhecidos.

`PATCH /profile/contactName/:owner/:instanceName` altera o nome de um contato individual usando a autenticação e o escopo da instância. Recebe `{ "remoteJid": "5511999999999@s.whatsapp.net", "name": "Dentista" }`; aceita PN/LID, normaliza sufixos de dispositivo, exige nome não vazio de até 200 caracteres e rejeita controles, grupos, status e canais. `name` é aparado antes do envio. Não serve para mudar o nome do perfil da própria conta (`/profileName`).

A operação usa `addOrEditContact` do Baileys 7.0.0-rc14 com `fullName`, os aliases PN/LID conhecidos e `saveOnPrimaryAddressbook: true`. O [código oficial do socket](https://github.com/WhiskeySockets/Baileys/blob/master/src/Socket/chats.ts) aguarda a resposta da consulta de alteração de app-state e a persistência da versão antes de resolver. Portanto, a API só confirma depois dessa resolução; não afirma que o aparelho já aplicou a alteração. O campo de agenda primária solicita a sincronização ao WhatsApp, mas o provedor não oferece confirmação de gravação na agenda nativa do Android/iOS. Nenhum contato real foi alterado na validação automatizada.

O sucesso retorna `{ "success": true, "data": { "contact": { "id": "...", "name": "Dentista", "savedName": "Dentista", "savedNameUpdatedAt": "<ISO>", "nameSource": "saved" }, "syncedToWhatsApp": true } }`, incluindo aliases disponíveis. A API captura o horário após a confirmação, persiste o contato canônico e publica `contacts.upsert` independentemente de `emitOwnEvents`. Se apenas essa persistência/publicação local falhar após a aceitação remota, mantém o sucesso e acrescenta `data.syncPending: true`; o consumidor pode persistir o snapshot retornado sem repetir a alteração remota. Instância offline retorna 409; provedor sem o método, 501; falha na operação remota, 502 sem confirmação ou fallback local. Uma falha de rede pode ter resultado remoto incerto; não há nova tentativa automática nessa rota.

`POST /messages/readMessages/:owner/:instanceName` recebe `{ remoteJid, messageIds }` com 1 a 100 IDs por lote. Todos os IDs são validados na mesma instância/conversa antes de enviar qualquer recibo; IDs repetidos e mensagens enviadas pela própria conta não geram recibos duplicados. O backend do atendimento calcula o limite cronológico da mensagem visível e seleciona todas as mensagens anteriores elegíveis, enviando lotes para essa rota. A API não precisa consultar novamente o histórico inteiro para cada lote.

A API não baixa anexos recebidos durante a importação ou no webhook de mensagens: persiste o payload e as chaves necessárias para recuperar os arquivos quando solicitados. O download ocorre na rota explícita `/media/download`; o frontend/backend decide quando a mídia está visível. O download do pacote de sincronização pelo Baileys e a obtenção de arquivos para um envio solicitado são operações diferentes dos anexos recebidos.

`POST /profile/fetchProfilePicture/:owner/:instanceName` sempre consulta o provedor, sem cache local da URL. Não exige parâmetro `refresh`. O resultado fica em `data.status` (URL ou `null` para foto ausente/restrita); falhas transitórias retornam erro, para que não apaguem uma foto conhecida. A consulta usa prazo de 10 segundos e rejeita resultado tardio de uma sessão desconectada.
